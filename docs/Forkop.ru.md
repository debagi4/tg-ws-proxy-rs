# Telegram через SOCKS5 и Forkop

[English guide](Forkop.md)

SOCKS5-вход позволяет направлять TCP-трафик Telegram из Forkop в существующий
WSS-транспорт `tg-ws-proxy-rs`, сохраняя пул соединений и настройки Cloudflare/fallback.
Виртуальный интерфейс не создаётся. Обычный MTProto-вход продолжает работать параллельно.

```text
Telegram без прокси в приложении → Forkop → SOCKS5 127.0.0.1:1080 → WSS → Telegram
```

## Что установить

Нужны бинарник **и LuCI-пакет из этой ветки/версии**. Редактирование UCI не добавит
SOCKS в старый бинарник. Обычный upstream-установщик скачивает опубликованный релиз,
а не эту неопубликованную ветку. Сборка описана в [Building.md](Building.md),
упаковка LuCI — в `openwrt/build-luci-package.sh`. Для Cudy TR3000 нужен Linux ARM64
musl; бинарник, собранный обычным `cargo build` на Mac, на роутер не подходит.

## Включить SOCKS

Открой **Services → Telegram WS Proxy (Rust) → General**:

- Включи **Enable SOCKS5 input**.
- Адрес: **127.0.0.1**.
- Порт: **1080**.
- Сохрани настройки и перезапусти службу.

Эквивалентные команды для уже установленной и настроенной службы:

```sh
uci set tg-ws-proxy-rs.main.socks_enabled='1'
uci set tg-ws-proxy-rs.main.socks_host='127.0.0.1'
uci set tg-ws-proxy-rs.main.socks_port='1080'
uci commit tg-ws-proxy-rs
/etc/init.d/tg-ws-proxy-rs restart
logread -e tg-ws-proxy-rs
```

В логе должна появиться строка `SOCKS5 Telegram listener: 127.0.0.1:1080`.
Если порт занят, запуск службы завершится ошибкой. Автозапуск у обоих входов общий.
MTProto-порт и секрет менять не нужно.

Для обычного запуска: `tg-ws-proxy --socks-enabled --socks-host 127.0.0.1 --socks-port 1080`.
Переменные окружения: `TG_SOCKS_ENABLED`, `TG_SOCKS_HOST`, `TG_SOCKS_PORT`, `TG_SOCKS_DC`.

SOCKS не требует пароля. Для Forkop на том же роутере оставь loopback. Если нужно
прописать SOCKS непосредственно в Telegram на устройствах локалки, укажи LAN-адрес
роутера в настройке прослушивания. Доступ должен оставаться только у доверенных
устройств; открывать порт в WAN не требуется.

## Настроить Forkop

Начни с одного компьютера, сохранив старый рабочий маршрут:

1. Создай секцию `telegram_ws`, действие **Connection / Подключение**.
2. В поле **Connection URL** укажи `socks5://127.0.0.1:1080`, без логина и пароля.
   **Mixed Proxy** не включай: это другой вход в сам Forkop.
3. В **Device filter / Фильтр устройств** укажи IP тестового компьютера, например
   `192.168.1.171/32`. Не выбирай **Forced device routing**: оно отправит сюда весь
   трафик устройства. Не добавляй адреса самого роутера.
4. Направь сюда только **TCP к IP дата-центров Telegram**. Удобно использовать
   пользовательский rule set, приведённый ниже. В его настройках включи учёт подсетей/IP:
   Forkop может игнорировать их по умолчанию.
5. Поставь правило перед другими правилами для тех же адресов и устройства.
   UDP/звонки и Telegram Web оставь на другом подходящем маршруте, например AWG/VLESS.
6. Отключи прокси в самом Telegram и полностью перезапусти приложение.

Пример `/etc/forkop/telegram-ws.json` — **неполный тестовый список DC2**:

```json
{
  "version": 3,
  "rules": [{
    "network": "tcp",
    "ip_cidr": ["149.154.167.50/32", "149.154.167.51/32", "149.154.167.222/32"]
  }]
}
```

Выбери этот файл в поле **Rule sets** секции. Расширяй список реальными адресами DC,
которые использует твой Telegram. Встроенные привязки перечислены в
[`src/socks.rs`](../src/socks.rs). Не направляй сюда весь набор доменов Telegram:
`t.me`, HTTPS и веб-версия не являются поддерживаемым MTProto-трафиком.

**Защита от зацикливания:** фильтр устройства должен охватывать клиентский компьютер,
а не роутер. Исходящие WSS/CF/TCP-соединения самого прокси не должны снова попадать
в его SOCKS-вход. Если другие правила захватывают трафик роутера, добавь для этих
соединений исключение/отдельный рабочий выход. Не указывай собственный SOCKS-порт
в поле **Outbound proxy URL** у `tg-ws-proxy-rs`.

SOCKS должен получать реальный IP назначения, а не FakeIP или имя домена.
При правилах на основе доменов проверь настройку Forkop **Resolve real IP for routing**.
Рабочий VPN и посторонние DNS-настройки для этого менять не требуется.

## Привязки DC и ограничения

Для нового известного адреса есть **SOCKS5 destination DC mappings**. Формат —
`DC:IP`, отрицательный номер означает media DC. Например:

```sh
uci add_list tg-ws-proxy-rs.main.socks_dc='-2:149.154.167.222'
uci commit tg-ws-proxy-rs
/etc/init.d/tg-ws-proxy-rs restart
```

Явные привязки перекрывают встроенные; последняя запись для адреса побеждает.
Это адреса, к которым обращается **клиент**, а не настройка upstream `--dc-ip`.
Номер DC нельзя угадывать по подсети. Для IPv6 нужны явные привязки. Неизвестные
адреса отклоняются с сообщением `has no DC mapping`.

Поддерживаются SOCKS5 CONNECT на порты 80/443/5222 и MTProto abridged/intermediate/
padded intermediate, обычный и обфусцированный без секрета. Не поддерживаются
SOCKS UDP/BIND, произвольные сайты/доменные имена, MTProto Full/HTTP и MTProxy/FakeTLS
внутри SOCKS. Звонки через этот TCP-мост не обеспечиваются.

SOCKS подтверждает CONNECT до установки WSS: клиент только после этого отправляет
MTProto-заголовок. Поэтому одного успешного CONNECT недостаточно для проверки обхода.

## Проверить и откатить

Проверь отправку сообщений, загрузку и отправку файлов. В Forkop соединение должно
попадать в `telegram_ws`, в логе прокси — идти через WS/CF с передачей байтов.
`TCP fallback` означает работу запасного прямого подключения, а не успех WSS.
Обычный тест задержки через HTTP-сайт для этого SOCKS не подходит.

При проблемах сначала выключи тестовую секцию Forkop и верни прежний маршрут.
Затем выключи **Enable SOCKS5 input** и перезапусти службу. Перезапуск общей службы
прервёт текущие соединения, но настройки прежнего MTProto-входа сохраняются.

В бэкап нужны `/etc/config/tg-ws-proxy-rs`, `/etc/config/forkop` и пользовательский
rule set (если `/etc/forkop/` уже добавлен, файл входит в него). Бинарник и зависимости
бэкап настроек не переустанавливает: сохрани соответствующую сборку отдельно.

Автотесты проверяют протокол и передачу через тестовый WebSocket. Реальная работа
клиентов Telegram через Forkop на физическом роутере ещё требует проверки.
